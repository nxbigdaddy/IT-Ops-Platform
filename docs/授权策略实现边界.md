# 授权策略实现边界

第15轮新增纯函数OperationAuthorization，用于测试未来后端权限规则；**当前未接身份认证中间件、未应用于现有Demo API，不能作为生产安全完成的证据**。

## 规则

- 角色：Viewer、Operator、Approver、Administrator。未知枚举拒绝。
- 全部角色读取均须在明确站点范围内；管理员不绕过范围，不支持通配符。
- Operator/Administrator可编辑草稿；Approver/Administrator可审批，但不能批准自己的请求。
- Operator/Administrator申请执行需独立批准记录；策略返回Allowed也不触发执行，ExecutionEnabled固定false。
- 身份、资源或范围缺失默认拒绝，错误只含安全代码。

## 信任边界

AuthorizationContext只能由未来认证层从经验证身份与服务器端授权库构造，不能接收客户端自行声明的角色/站点数组。OperationResource的RequestedBy/Approved/ApprovedBy必须来自服务器端可信记录，不能把请求正文的布尔值当成审批凭证。

第16轮新增独立ApprovalBinding快照校验：资源ID/版本、请求人、64位小写十六进制摘要必须匹配；审批时间不得晚于当前时间，到期时刻即失效，撤销/已使用/自审拒绝。它不计算或签名摘要，也不修改记录；相同未消费快照可重复校验，因此不能独立防重放。本策略仍不验证审批人当时的资格、可信双人复核来源或并发变更。因此真实任务执行仍须：重新加载资源并授权，校验不可变审批记录与操作摘要，事务性消耗批准并创建任务，审计执行身份/来源，再交给受限Worker。AI提示词和模型输出不得直接构造可信身份或批准记录。

第17轮新增OperationDigest：固定schemaVersion=1和字段顺序、参数按Ordinal键排序、UTF-8 JSON编码后SHA-256小写摘要。资源ID/版本/动作/参数全部绑定，JSON转义避免分隔符歧义；Unicode不额外归一化，调用方不得先后采用不同规范；第20轮起拒绝孤立UTF-16代理字符，合法代理对继续支持，避免编码替换歧义。参数最多32项、值2000字符，标识符仅ASCII字母数字及有限分隔符。摘要不是签名或加密，也不应包含真实秘密；secret应引用版本化标识。动作名称仅语法校验，不代表已在执行白名单内。授权策略/绑定策略/摘要生成仍未接入API或任务调度。

### schemaVersion=1 固定测试向量

以下无换行UTF-8字节（仅ASCII样例）的SHA-256由独立Node crypto计算，并由后端固定断言：

```json
{"schemaVersion":1,"resourceId":"demo-target","resourceVersion":1,"action":"inspect","parameters":{"a":"one","b":"two"}}
```

摘要：`8eb0602658d243a7bc1baf879c687ca7cfeafbaabb19b4020199bbfb70be1d06`。

更改字段顺序、JSON转义策略或规范版本须明确迁移，不能静默重新解释已批准摘要。此ASCII向量不构成跨语言Unicode序列化全面兼容证明，当前规范使用.NET Utf8JsonWriter默认转义行为。

第19轮新增ExecutionPreflight组合入口：先检查角色和站点，再从OperationDraft重新计算摘要，最后检查审批绑定/有效期/撤销。调用方不能另外传入一个与当前参数脱节的摘要以绕过组合校验。结果EligibleSnapshot仅表示这些快照满足规则，ExecutionEnabled与ApprovalConsumed固定false。仍须可信存储、并发版本控制与事务消费；不能直接把HTTP请求绑定为这些可信对象。

现有Demo仍只限开发/本机，不能对外暴露以替代企业认证。前端反馈的“已验收”只是模拟流程状态，与此授权策略、真实审批完全无关。

## 提示词发布的审批记录（第217轮）

提示词发布现在**必须携带审批记录**：`approvalReference`（形如 `approval://prompt/<小写标识>/<正整数>`）与 `approvedBy`（1–64字符、无控制字符），二者写入该条不可变发布修订，并出现在发布历史、详情响应与绑定视图中。

规则边界：

- **一个审批引用只能授权一次发布**（跨提示词生效）；重复使用返回 409 `approval_reference_reused`，与“同一草稿版本已发布”（409 `already_published`）区分开。
- 校验顺序：未知提示词 404 → 字段形状 400 → 已发布 409 → 引用复用 409 → 版本冲突 409。被拒请求**不回显**提交的审批人名称，且不产生任何发布修订。
- **这不是权限控制**：原型没有鉴权，审批人名称无法证明身份，也没有任何审批系统集成；“两人规则”“审批时效”“撤销发布”均未实现。它只是把“发布需要一条审批记录”变成可校验、可追溯的流程约束，不能替代真实审批与职责分离。

## 组合执行门禁的可评审入口（第164轮）


`ExecutionPreflight` 也开放为只读预检：`GET /api/v1/execution-scenarios` 与 `POST /api/v1/execution-preflight`。十一个场景展示三道门禁的**真实顺序与停止点**：角色与站点授权 → 按当前草稿重算动作摘要 → 审批绑定与有效期。场景结论一律取自 `ExecutionPreflight.Evaluate`，阶段列表只用于显示在哪一步停止，因此面板显示与真实门禁不可能给出不同判定（xUnit 对此做了一致性断言）。

覆盖：三道门禁通过（仅快照自洽）；授权阶段停止（站点越权、观察者请求、无审批、自批）；摘要阶段停止（草稿无法规范化）；审批阶段停止（过期、撤销、已使用、摘要不符、版本不符）。任何场景都不启用执行、不消费审批，前端面板只做场景选择与展示。

## 角色与站点授权的可评审入口（第163轮）

`OperationAuthorization` 的规则同样开放为只读预检：`GET /api/v1/authorization-scenarios` 与 `POST /api/v1/authorization-preflight`。十四个场景覆盖观察者只读、运维编辑、审批人批准他人、独立批准后请求执行（允许），以及观察者编辑/请求执行、运维审批、站点越权、自批、未批准或自批后请求执行、未知角色、缺身份、缺资源（拒绝）。每个结论都由 `OperationAuthorization.Diagnose` 实际求值，返回结论代码与逐条规则结果（身份、资源合法性、角色动作、站点范围、批准独立性）。

规则保持原样：无通配站点、无大小写折叠、**管理员也没有站点旁路**。这些接口只返回快照判定，`executionEnabled` 与 `productionEnabled` 恒为假，且不含任何真实鉴权；前端“角色与站点授权预检”面板只做场景选择与展示。两个场景面板共用 `scenario-preflight.ts` 的响应校验，避免两套规则视图出现不同判定口径。

## 审批绑定的可评审入口（第162轮）

`ApprovalBinding` 的规则现由 `GET /api/v1/approval-scenarios` 与 `POST /api/v1/approval-preflight` 暴露为**只读预检**：服务端用固定合成输入运行同一套规则，返回结论代码与每条规则的通过情况（存在审批证据、变更字段合法、未撤销、未使用、有效期、审批人独立、绑定一致）。场景覆盖有效快照、缺少审批、已撤销、已使用、自批、摘要不符、版本不符、已过期、尚未生效、变更本身不合法十种，每个拒绝场景恰好只有一条规则未通过，便于定位。

这些接口**不授权执行**（任何场景 `executionEnabled` 与 `productionEnabled` 均为假），也不代表真实审批已存在：授权判定、审批消费、审计与任务入队仍未实现。前端“审批绑定预检”面板只负责场景选择与展示，规则结果全部来自后端求值，不包含本地判定。
