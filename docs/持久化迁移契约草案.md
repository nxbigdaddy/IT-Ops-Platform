## 2. 平台数据库与监控目标分别决策

- **平台 DB** 存储平台自己的任务、版本、历史、幂等记录、反馈和将来可能需要的 Outbox。设计基线选择 EF Core + Npgsql + PostgreSQL 16；本文沿用该目标，不据此声称依赖兼容性、连接、迁移或备份恢复已验证。实际实施仍须核实受支持版本、事务隔离、唯一约束、HA、恢复演练和容量。
- **被监控/管理目标** 可以是不同厂商网络设备或不同数据库产品；其连接器协议、只读账号、采集频率与支持矩阵另行审批。能监控某数据库，不代表平台 DB 使用它；平台选择 PostgreSQL，也不代表已具备监控 PostgreSQL 或所有数据库的能力。
- **平台自身监控指标** 如 DB 延迟、事务失败、未知提交和保留清理积压属于可观测性目标，不能与被监控设备接入范围混同。
- 此次仅文档设计。禁止为验证本草案探测设备、建立目标连接、下发命令或修改生产数据。

## 3. 未来异步接口与取消语义

以下是接口形状建议，名称、DTO 和 HTTP 映射尚未实现或冻结：

```csharp
Task<WriteOutcome<TaskView>> CreateAsync(CreateTaskCommand command, CancellationToken ct);
Task<TaskReadView?> ReadAsync(Guid taskId, CancellationToken ct);
Task<WriteOutcome<TaskView>> ApplyAsync(ApplyTaskCommand command, CancellationToken ct);
Task<WriteOutcome<FeedbackView>> AddAsync(AddFeedbackCommand command, CancellationToken ct);
Task<FeedbackPage> ListAsync(FeedbackQuery query, CancellationToken ct);
Task<OperationView> GetOperationAsync(OperationQuery query, CancellationToken ct);
```

命令携带作用域、操作类型、幂等键、规范化请求摘要和关联标识；`Apply` 还携带 `expectedVersion`。操作者、组织和授权范围由服务端可信上下文提供，不接受请求体自报权限。所有 DB I/O、事务开始、查询和可取消等待都传播取消令牌，不以 `Task.Run` 包装同步存储冒充异步持久化。

取消必须按时间点区分：

1. 尚未发起写入，或能确认事务回滚：报告取消且明确未提交。
2. 正在提交、连接中断或请求取消，但无法确认数据库最终结果：进入 `CommitUnknown`，不能返回“已回滚”或“肯定未保存”。请求断开后未必能向该请求返回错误，服务端仍需记录关联标识并支持恢复查询。
3. 已确认提交成功：保留成功事实；迟到的取消不撤销事务。客户端未收到响应时，通过同一幂等键查询结果。
4. 操作取消仅停止等待/尽力中止 I/O，不等于取消业务任务；业务取消应是授权后、具有版本前置条件的独立状态转换。

## 4. 任务事务：CAS、历史与一致读

### 4.1 不变量与最小数据约束

- `tasks` 保存任务 ID、作用域、状态、单调递增版本与更新时间；初始版本与现有 Demo 对齐为 1。
- `task_history` 保存任务 ID、前后状态、事件、结果版本、操作 ID、操作者引用和 UTC 时间；对 `(scope, task_id, version)` 建唯一约束，历史只追加。
- `operations` 保存作用域、幂等键、规范化请求摘要、操作 ID、可恢复结果或结果引用；幂等作用域有数据库唯一约束。
- Demo 的进程内全局 `Sequence` 不应直接承诺为数据库全局提交顺序。单任务排序以版本为准；若提供全局游标，须单独定义可见性与分页语义。
- 当前 Demo 创建任务不追加转换历史。迁移应保留该区别：版本 1 是创建快照；若增加创建审计，单独定义事件，不能伪造状态转换或宣称已迁入旧历史。

### 4.2 单次 Apply 的事务边界

1. 校验身份、资源范围和命令格式，开启事务；按幂等键认领或检查既有操作。同键同摘要已成功时先返回原结果，不再用已变化的版本重复执行 CAS。
2. 校验任务存在、当前版本与允许的生命周期转换。通过条件更新 `WHERE task_id = ... AND version = expectedVersion` 完成 CAS；只允许影响一行，并将版本增加一次。
3. 在同一事务内追加恰好一条对应结果版本的历史，记录幂等完成结果；如果以后引入事件发布，Outbox 也必须同事务写入，外部发送不能放在事务内。
4. 提交成功才报告已提交；CAS 未命中返回明确的版本冲突或不存在结果。非法转换、版本冲突、历史插入失败均不能留下仅状态成功或仅历史成功的半更新。

进程内锁不能替代数据库 CAS。EF 跟踪实体、单次读取或简单 `SaveChanges` 本身也不能证明这些不变量；需用并发条件、唯一约束和真实数据库集成测试验证。数据库异常应映射成稳定业务结果，不向客户端泄漏 SQL、连接串或原始异常。

### 4.3 一致读

状态和历史必须来自同一逻辑快照：使用适当的快照/可重复读事务或满足一致性的单次查询，不在普通读已提交隔离下执行两个彼此无约束的查询。返回不可修改的 DTO/数组，不暴露被跟踪实体。分页历史返回快照版本或上界；后续页不得把新历史拼入旧快照。只读副本的滞后必须显式标记，不能用于证明写入不存在或解决提交结果未知。

## 5. 幂等、未知提交与重试边界

### 5.1 幂等键合同

- 创建任务、状态转换和提交反馈均要求客户端或可信调用方为一次业务意图提供稳定幂等键。作用域建议为组织/租户 + 调用主体或客户端 + 操作类型 + 键；目标 ID、预期版本和有效载荷纳入规范化摘要。
- 同键同摘要：返回原操作 ID、资源 ID、提交版本及等价结果，不新增任务、历史或反馈。不得因服务端重新生成时间戳/UUID而改变摘要；这些值首次提交时确定并复用。
- 同键不同摘要：返回 `IdempotencyKeyConflict`，不覆盖、不执行；并发同键须通过数据库唯一约束串行决策，不能仅靠“先查再插”。
- 尚在处理的同键返回明确 `InProgress` 或查询引用，不伪装成功。幂等结果查询同样校验原作用域与当前读取权限，不能借键查询他人数据。
- 幂等键保留期必须覆盖客户端重试、恢复与对账窗口；具体期限待评审。过期后不可假定仍可安全重放；必要时保留精简墓碑/摘要。不得因清理记录导致旧请求被静默当成新请求执行。

### 5.2 结果分类与恢复

建议结果至少区分 `Committed`、`Rejected`（校验/权限/版本/幂等冲突）、`NotFound`、`CancelledBeforeCommit`、`UnavailableBeforeCommit` 和 `CommitUnknown`。HTTP 状态码不是持久化事实；错误载荷还需表达稳定错误码、操作 ID、查询方式及是否允许重放。尤其不可仅因返回 5xx 就认为事务失败。

`CommitUnknown` 的典型场景是 DB 已提交但响应丢失、提交调用超时、取消与提交竞态。恢复路径：用原幂等键或操作 ID 到权威库查询；查到已完成则回放结果，仍处理中则等待/对账。查无记录但旧事务可能仍在途时，不能立即认定未提交；须依据事务终止证据，或依靠相同幂等键的数据库唯一约束协议安全收敛。数据库不可用时维持未知并告警，不生成新键绕过对账。

### 5.3 不自动重试非幂等操作

- 不为任意写请求、反馈 `Add`、任务创建或未来设备变更配置通用自动重试；必须先有可验证的持久幂等合同。
- 只读操作可做有界退避与抖动重试，服从总截止时间和取消；已明确回滚的写事务只有满足完整幂等协议时才可有界重试。
- 版本冲突、权限拒绝、非法转换和键冲突不自动重试。未知提交首先查询/对账；不得用新键或最新版本偷偷重放原意图。

### 5.4 当前已有的 Demo 内存语义（非生产）

第155轮起，部署草稿新增必填的 `Host` 字段，并与采集目标共用“仅文档保留地址”策略：只接受 `192.0.2.0/24`、`198.51.100.0/24`、`203.0.113.0/24`、`2001:db8::/32` 或小写、以 `.invalid`/`.example` 结尾的主机名；其它取值返回 `host: not_documentation_target` 且不回显提交值。这样草稿不可能携带真实数据库地址。

仓库现有一个仅进程内存的 `DemoOperationLedger`，用于把上述规则固化成可测试语义：同键同摘要已提交时返回 `ReplayCompleted` 与原操作 ID/结果版本，同键不同摘要返回 `PayloadConflict`，仍处处理中返回 `PendingConflict` 且不覆盖首个操作 ID，结果未定返回 `ReplayUnknown` 并标记需对账；任何结果都不授予自动重试，容量上限为拒绝而非淘汰。它**没有**持久化、跨实例唯一性、过期/墓碑或权威查询接口，因此不能替代数据库唯一约束与恢复查询，也不是生产幂等实现。

第143轮补充了只读可观测与对账入口：`GET /api/v1/demo-operations` 返回上限、已登记数、待处理/已提交/结果未知计数与剩余名额；`GET /api/v1/demo-operations/{operationId}` 用于按操作 ID 对账查询，返回该记录的 scope/operation/key/digest/state/resultVersion/resultReference，未找到时明确 404 且不得据此推断“未提交”。两者都只描述当前进程，**不授予重放权限**；真实实现必须在查询时校验作用域与权限，不能借操作 ID 读取他人数据。
- EF 执行策略、驱动、中间件、网关、前端和后台消费者的重试必须统一审查，避免多层叠加。数据库事务和幂等记录只保证平台内一次逻辑提交，**不保证外部设备副作用“恰好一次”**。
- 本草案不新增 Worker 或连接器。未来非幂等设备操作即使有平台幂等键，也必须另立执行凭据、审批、设备侧去重/回读和人工对账方案；未知执行结果不得自动重发。

## 6. 反馈保留：禁止静默丢弃

当前 Demo 的第 201 条反馈会移除最旧一条，这是已存在的演示容量策略，不能作为未来生产合同继承。

1. **成功条件**：只有持久提交得到确认才返回保存成功；提交结果未知显式标记。不得捕获存储失败后返回成功，不得降级写入易失内存后继续声称已持久化。
2. **容量策略**：数据库/配额不足时明确拒绝新提交并返回可操作错误和关联标识，同时告警；已有记录保持不变。若选择缓冲队列，必须另行验证持久性、限额和恢复，不得引入无通知丢弃。
3. **保留规则**：由数据负责人批准保留周期、归档/删除条件、法律保留例外、用户告知与导出权限；本草案不虚构已批准天数。禁止以“最近 200 条”为生产清理依据。
4. **清理可审计**：按审批策略分批清理，记录策略版本、时间边界、数量和结果；失败可恢复、可告警。受保留冻结约束的数据不得删除。备份副本的到期和恢复后再清理策略同时明确。
5. **稳定读取**：按 `(created_at, id)` 降序游标分页并绑定授权范围，规定分页快照语义；不因分页限制或界面只显示最近记录而实际删除旧反馈。
6. **最小化与安全**：保留现有输入校验，但提示“不含秘密/个人数据”不能保证用户不会提交这些内容。需明确访问范围、传输/静态保护、日志脱敏与受控删除流程；指标和错误日志不记录反馈正文。

## 监控查询的只读筛查（第196轮）

被监控数据库目标的采集语句新增只读筛查：`POST /api/v1/monitored-query-preflight` 接受一条计划语句，按**关键字与函数名单**判定，返回是否通过、识别类型（select/show/with/unsupported）、长度与结论代码。拒绝码包括 `multiple_statements`、`comments_not_allowed`、`not_read_only`、`too_long`、`write_keyword_<关键字>`（insert/update/delete/into/set/drop/alter/copy 等）与 `write_function_<函数>`（pg_terminate_backend、pg_cancel_backend、pg_reload_conf、set_config、nextval、lo_import 等）。

该预检**不连接数据库、不执行语句、不做语法解析**：通过只表示未命中已知写入特征，不能证明语句无副作用；真实采集仍需要只读账号、查询白名单与审计。接口同样受 Demo 门控（生产 503、外域 403），并拒绝未知请求字段。

## 7. 迁移、上线门禁与可观测性

迁移目标以只读清单形式暴露：`GET /api/v1/migration-plan` 列出未来持久化必须建立的八张表（反馈记录、提示词草稿/版本/发布修订、任务快照与历史、操作台账、功能登记）及其标识列、唯一约束与注意事项；每个步骤都带 `executed=false` 与 `productionEnabled=false`，接口只读且**没有**执行端点。该清单是评审输入，不是迁移记录：它不代表已建表、已迁移或具备事务能力。

关键约束由清单显式声明：台账身份 `(scope,operation,key)` 与 `operation_id` 唯一；任务历史 `(task_id,sequence)` 唯一；提示词版本与发布修订各自 `(prompt_id,version)` 唯一且只允许追加。清单与实现的一致性由 xUnit 断言（每个内存存储在计划中都有对应步骤、唯一约束必须存在、任何步骤都不得声称已执行）。

为避免业务端点直接绑定进程内实现，后端已明确三类端口，均以 `TryAddSingleton` 注册，因此测试或未来的持久化实现可以**先行注册并覆盖**：

**首个可替换实现（第203轮）**：`IDemoFeedbackStore` 已有**非生产**的文件实现 `JsonFileFeedbackStore`——单进程、单文件、先写临时文件再原子替换、容量沿用200条（超出丢最旧），不提供事务、并发写者、跨实例协调或版本化迁移。启用方式：

```bash
ASPNETCORE_ENVIRONMENT=Development Demo__Enabled=true Demo__FeedbackFile=/tmp/ops-demo-persistence/feedback.json dotnet run --project src/backend/OpsPlatform.Api
```

**第二个可替换实现（第204轮）**：`IOperationLedger` 也有非生产的 `JsonFileOperationLedger`——语义与内存实现一致（先认领再执行、结算或标记未知、容量500拒绝而不淘汰、`Release` 仅用于确认未提交），只增加写穿透与原子替换。启用：`Demo__OperationLedgerFile`。两者同时启用后已做**真实进程级验证**：用同一幂等键提交反馈，重启后端进程后重放同键返回 **200 且同一条记录 id**，反馈列表仍只有 1 条（未产生重复写入），台账摘要显示 completed=1 且 `persistent:false`——契约仍不声称持久化。注意：任务存储仍为内存实现，因此跨重启重放只对了反馈路径成立；跨重启的**任务**重放需要任务存储也具备持久化实现（未实现）。

**第三个可替换实现（第205轮）**：`IDemoTaskStore` 也有非生产的 `JsonFileTaskStore`——保留内存实现的 CAS 语义（比较版本、追加流水、替换状态，同一进程内原子），增加写穿透与原子替换；容量100、损坏文件改名隔离。启用：`Demo__TaskFile`。与文件台账同时启用后已做**真实进程级验证**：创建任务并批准（版本1→2）→ **重启进程** → 用同一幂等键重放 → 返回 200 且 `code=replayed`、版本仍为2、历史仍为1条（未重复执行）。

因此跨重启的**任务**重放现在成立，但请注意边界：进程内互斥只在单个进程内有效，两个进程写同一文件会丢失其中一次更新；没有任何过期、墓碑清理或多实例协调。演示与试点仍应把它当作“可运行证据”，而不是生产幂等实现。

**第四个可替换实现（第207轮）**：提示词草稿与版本状态也可落到文件（`Demo__PromptStateFile`）。它与前三个不同的一点很关键：**变量 schema 永远来自代码**，文件只能替换版本内容与已发布修订；未知提示词 id 一律忽略，不能通过文件新增提示词或放宽占位符。已做真实进程级验证：新增草稿版本并发布 → 重启进程 → 草稿版本与已发布修订均保留，且存储模式视图报告该端口为 `development-file`、`durable=false`。限制：单进程、无事务、无审批与生效流程。

## 关系型持久化落地（第227轮，EF Core + SQLite，本地开发）

`Demo__SqlitePath=<数据库文件>` 时，**全部四个端口**（反馈存储、幂等台账、任务存储、提示词状态）改为真实数据库实现（`OpsPlatformDbContext` + SQLite）：

- **唯一性由数据库保证**：`demo_operation_ledger` 上对 `(Scope, Operation, Key)` 建立**唯一索引**；两个写入者同时认领同一键时，其中一个 insert 被索引拒绝，代码捕获后重读该行并按重放/冲突语义返回——不再依赖进程内字典。
- **真实事务**：反馈写入后按容量裁剪最旧行，裁剪与插入在同一事务内提交。
- **条件更新**：完成/标记未知/释放都是带条件的 `ExecuteUpdate/ExecuteDelete`（要求仍是本操作的 pending/unknown 行），影响行数不为 1 即视为失败；任务迁移用 `WHERE Id AND Version=期望值` 的条件更新实现 CAS，流水与状态同事务提交，两个写入者竞争同一期望版本时恰好一个成功。
- 排序用 UTC 毫秒存储：SQLite 不支持对 `DateTimeOffset` 排序（实测报 `NotSupportedException`），因此表中保存 `CreatedAtUnixMs` 并在读取时还原为时间点。
- 提示词状态用 `(PromptId,Version)` 唯一索引与事务内整表替换；变量 schema 仍由代码拥有。
- **提供程序可换**：同一套存储实现可跑在 SQLite（`Demo__SqlitePath`）或 PostgreSQL（`Demo__PostgresConnection`）之上；模型与存储代码不感知具体提供程序，选型只发生在 `RelationalModeSelector`。
- **连接目标受限**：连接串的主机必须是本机回环、RFC 5737/3849 文档保留地址或 `.invalid/.example` 名称，否则该模式直接视为未配置——原型不可能被指向真实数据库；就绪报告只输出提供程序名，不回显连接串或主机。
- 数据库文件由 `EnsureCreated()` 建立，**没有迁移历史、保留策略、行级安全或审计**；响应契约仍报告非持久化（`persistence: none/memory`），`/api/v1/storage-modes` 会把这两个端口标为 `sqlite` 且 `durable=false`、`productionReady=false`。

已做真实进程级验证：以 SQLite 启动 → 存储模式显示两个端口为 `sqlite` → 写入一条带幂等键的合成反馈 → **重启进程** → 记录仍在、同键重放返回 200 且不产生第二行。**这不是生产持久化**，SQLite 仅用于本机演示真实事务与唯一约束。

未配置该键时仍使用内存实现（本机默认）。已实测：配置后写入一条合成反馈并**重启进程**，记录仍在；接口响应依旧报告 `persistence: "memory"`（不因文件存在就声称已持久化），就绪检查仍为 503。损坏文件不静默删除，而是改名为 `feedback.json.<原因>-<时间戳>` 留待排查后以空集合启动。这把“端口可替换”从声明变成可运行证据，但**不是**生产持久化，也不替代数据库唯一约束与事务。

- `IDemoFeedbackStore`：反馈记录存储（容量、按编号读取）。
- `IDemoTaskStore`：任务快照与迁移历史存储。
- `IOperationLedger`：幂等台账协议——`Claim`（先认领再执行）、`Complete`/`MarkUnknown`（后置结果）、`Release`（明确失败时释放）、`Get`/`Find`（按身份或按操作ID查询）、`Summary`（只读摘要）。端点只依赖接口，不再依赖具体类；测试用记录型替身替换该端口，验证迁移流程确实先认领、后完成，且重放不会重复完成。
- `IPromptCatalog`：提示词**读取**端口（列表、单项、功能绑定）。写路径（新增版本、恢复、发布）仍由持有校验与版本规则的 `PromptService` 处理，因为持久化替换不应绕过规则；替换读取端口不会影响写语义。测试用只读替身证明读取端点走端口、写端点仍走规则所有者。

端口存在**不代表**已实现持久化：当前实现仍是进程内存，重启即丢失，且不含跨实例唯一约束、过期/墓碑与事务消费。替换该端口时必须保持协议语义——重放查询不得授予重试、`Release` 只用于确认未提交的场景，结果未知必须走对账而不是自动重试。

建议分阶段实施，均为待办：

1. 评审并冻结异步 DTO、错误分类、幂等窗口、保留政策、授权边界和事务不变量；明确负载假设、延迟目标、RPO/RTO 的负责人和数值。未批准的目标不能写成已达标 SLO。
2. 在隔离测试环境新增适配器、约束和版本化迁移；使用真实 PostgreSQL 集成测试，不用内存 provider 代替事务/CAS 证据。
3. 保留 Demo 模式与标签，持久化模式采用显式配置和独立验收。缺少 DB 配置或连接失败时不得默默回退内存。模式切换不自动把模拟审批/执行状态当成真实业务记录。
4. 现有内存数据默认不承诺迁移。确需保留时，另行批准维护窗口和一致快照导出/导入，保留 Demo 来源、校验数量/版本/历史并去重；不能在进程已退出后声称恢复不存在的内存数据。避免无一致性方案的双写。
5. 备份恢复、索引升级、兼容回滚、数据校验和故障演练通过后再评审上线。回退应用不等于回退数据；不可通过切回内存隐藏持久化故障或丢失已确认提交。
