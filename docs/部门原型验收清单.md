# 部门原型验收清单

> 版本：v0.1；日期：2026-10-10。**本文是目标与原型验收规范，不是已实现页面、已执行测试或部门已验收的证明。所有结果初始为“未执行”。**
> 基线：[整体系统设计方案](<整体系统设计方案.md>)；补充：[扩展兼容与 AI 配置设计](<扩展兼容与AI配置设计.md>)。
> 目标：前端优先交付使用部门体验并形成可回流反馈；数据库、API、连接器、权限和 AI 并行实现。原型不得冒充真实业务系统。

## 1. 交付层级与诚实标识

| 层级 | 可以证明什么 | 不可以证明什么 |
| --- | --- | --- |
| L0 原型可演示 | 页面、导航、合成数据、交互和反馈包可操作，核心流程自测有证据 | 生产鉴权、设备连通、持久化、真实 AI 调用、真实任务执行、部门认可 |
| L1 部门已评审 | 有真实参与者对具体版本提出反馈，评审记录/意见可追溯 | 所有意见已解决、生产可上线；无签认不能写“验收通过” |
| L2 获准只读试点 | 有后端授权、真实只读来源、批准环境、审计及最小化数据，完成试点门禁 | 生产写操作/全厂商兼容/全部部门正式验收 |
| L3 正式验收/上线 | 业务负责人真实签认，安全、恢复、运行保障和已约定范围均有证据 | 清单未覆盖的能力或未来版本天然通过 |

每页固定显示：版本/构建 ID、数据模式（模拟/真实/人工登记）、观察时间、验证范围和限制。原型角色切换只能标“角色展示模拟”，不是认证。模拟“保存”标明仅当前演示会话；刷新会丢失则事先提示并可导出反馈。不得提示“已写入数据库”“设备已恢复”“密钥有效”而没有对应后端证据。

每页底部提供统一的“记录本页意见”入口（全部17条路由同一实现）：它写入与“验收反馈”页相同的本机反馈数据，沿用同一敏感内容校验与导入契约，提交后不跳转，因此页面筛选与选中项保持不变；该入口不提交后端、不发送通知，也不代表部门签认。

## 2. 演示准备与数据集

### 2.1 执行前检查

- [ ] 记录 buildId、演示日期、浏览器/版本、屏幕/缩放、网络条件、演示者与观察者；未经同意不录屏或收集个人信息。
- [ ] 打包说明启动/访问方法、已实现交互、模拟项、未接接口、已知问题、反馈方式和退出/清理方法。
- [ ] 使用两个虚构部门 A/B、两个站点、观察者/运维/审批人/管理员展示角色；演示数据无真实员工、IP、账号、凭据或生产日志。
- [ ] 合成至少 30 个资产，覆盖 Windows/Linux/网络/虚拟化/打印/数据库目标；至少 12 条告警含各生命周期及未知，8 张工单，3 条备份记录分别覆盖成功、失败、无恢复验证。
- [ ] 准备空数据、无权限、未接入、加载、超时、部分失败、过期、未知、Unsupported 九类 fixture；不能只演示正常态。
- [ ] 禁用真实生产写操作和外发；原型 AI 使用合成样例明确标识，真实试点必须单独批准。
- [ ] 准备反馈导出位置与缺陷台账；自动检查可由开发完成，部门意见和签认栏保留“待部门填写”。

### 2.2 执行记录格式

每个脚本记录 `caseId、buildId、执行时间、执行者类型（自动/开发/部门）、模式、输入/fixture版本、预期、实际、结果、证据引用、feedbackId、复测版本`。结果仅限未执行/通过/失败/阻塞/不适用；不适用必须有范围依据。截图不包含秘密和个人信息。

模板中 `executor` 一律为 `未指定`、`result` 一律为 `未执行`：未执行的行不得声称由谁执行，一旦填写任何“非未执行”结果就必须同时填写执行者（`自动/开发/部门`）。
该格式已落成可校验的记录文件：`node scripts/prototype-case-records.mjs --template` 生成 `artifacts/prototype/case-records-template.csv`（按范围映射逐行给出 route 与 caseId，结果一律为“未执行”，不含任何预填通过），`--check <csv>` 校验必需列、用例与路由是否存在、取值是否合法、构建标识是否与当前构建一致，并要求“通过/失败”必须填写证据引用、已执行行必须填写执行时间、部门判定通过必须有关联反馈编号、“不适用”必须写明范围依据。校验通过只表示记录格式合规，**不表示任何用例已通过**。

评审结束后把填好的记录文件回填给开发即可生成进度汇总：`node scripts/render-review-progress.mjs --records <填好的csv>` 会先做同一套校验（失败即拒绝渲染），再输出 `artifacts/prototype/评审进度.md`——包含结果分布、失败/阻塞清单（含证据引用与反馈编号）、不适用依据、通过项证据、以及**仍未执行**的用例清单。该汇总只反映记录文件里实际填写的内容：未填写的行仍是“未执行”，也不会被描述为通过。

“通过”只在本次实际观察满足预期时填写。自动化或开发自测通过不代填部门通过。某页未实现，必须记录未实现/阻塞或明确排除当前批次，不得用占位页算完成。

## 4. 三条必须可演示的纵向流程

### D-01 日常排障（目标 10 分钟内）

首页发现异常→告警筛选→资产详情查看来源/质量→告警详情证据→转工单→指派与处理记录→回到告警关联→导出脱敏反馈。原型全部模拟动作应连续可见；不得请求生产权限。记录步骤完成数、耗时、求助次数和中断点。

### D-02 接入与可信配置（目标 8 分钟内）

连接器查看具体固件 planned→最小连接测试示例→识别模拟与真实差别→平台数据库页解释 provider≠监控库→AI 接入查看 allowlist/secretRef/预算→功能 prompt 查看审核发布和回滚→模拟 AI 不可用时转普通检索。

### D-03 异常与反馈回流（目标 8 分钟内）

切换 Partial/Stale→查看 Unknown 任务不能直接重试→键盘提交反馈→导出反馈包→重复导入去重→生成缺陷→关联修复版本→开发复测→保持“待部门确认”。没有真实部门复核，不允许自动关闭成“用户接受”。

## 5. 反馈字段、优先级与处理闭环

### 5.1 最小反馈 schema

| 字段 | 必填/说明 |
| --- | --- |
| feedbackId、schemaVersion、createdAt | 必填；UUID、版本、UTC；导出包另有 exportedAt 和 packageId |
| departmentAlias、reporterRole | 必填虚构/授权部门简称与角色；联系信息可选且单独保护，不要求真实姓名 |
| buildId、page/route、caseId、dataMode | 必填；定位版本、页面、脚本和模拟/真实/人工模式 |
| category、title、description | 必填；流程/功能/文案/可访问性/数据质量/兼容/隐私安全/性能/其他 |
| steps、expected、actual、reproRate | 缺陷必填；如 3/3，不将主观意见伪装可复现缺陷 |
| impact、affectedScope、priority、suggestion | 影响必填；优先级为提出值，分诊后另存 triagedPriority 和理由 |
| browserVersion、viewport、timezone、locale | 自动填充可预览；不收集设备指纹或未经同意的个人数据 |
| attachmentRefs、redactionConfirmed | 附件可选；上传/导出前脱敏检查，禁止 cookie/令牌/密钥/生产日志 |
| status、ownerAlias、issueId、targetIteration | 分诊后填写；明确责任人与迭代，不假造已承诺日期 |
| fixedBuild、retestEvidence、departmentDecision | 修复后填写；部门决定为待确认/接受/拒绝/需讨论，不能由程序代签 |

导出格式：UTF-8 JSON 为完整规范格式，CSV 为表格摘要；均带 schemaVersion、版本/范围/时区、总数及校验摘要。CSV 转义公式前缀（`= + - @` 及前导控制字符等），附件只用授权引用不嵌入秘密。JSON 按 schema/大小/类型验证，拒绝可执行内容和危险附件路径，不按导入包中的 owner/status 自动提权。

回流导入先预检→显示新增/重复/冲突→人工或已批准规则确认→按 feedbackId 幂等写入。重复包不得覆盖审核/部门签认；不同内容同 ID 进入冲突队列，保留源包摘要与操作审计。

### 5.2 优先级与分诊目标

| 优先级 | 定义/示例 | 目标处理规则（不是已承诺 SLA） |
| --- | --- | --- |
| P0 阻断 | 秘密/个人信息泄漏、越权、真实写操作误触、把模拟当真实导致决策风险 | 立即停用相关演示/功能并登记；未解决不得交付/上线，不能用风险接受跳过 |
| P1 高 | 核心流程中断、数据丢失、关键状态误导、键盘无法完成主流程 | 下一发布前修复并复测；当日完成分诊目标 |
| P2 中 | 非核心功能错误、可绕过交互问题、明显文案/可用性缺陷 | 两个工作日内分诊目标，明确目标迭代/绕行与责任人 |
| P3 改进 | 样式偏好、非必要增强、未来兼容建议 | 五个工作日内归类目标，形成候选 backlog，不承诺已实施 |

状态：New→Triaged→Planned→InProgress→FixedAwaitingRetest→Retested→AwaitingDepartmentConfirmation→Closed；可转 Duplicate/Deferred/Rejected，但必须有理由、关联记录和可追踪沟通。开发自测修复不自动等于部门确认；长期未回复保持待确认，不制造用户意见。

### 5.3 持续闭环，不要求用户逐步指挥

开发/主 agent 可自行完成分诊建议、复现、修复、检查、回归、生成发布说明、打包反馈和下一迭代清单。每轮输出新增/关闭/重开数量、P0/P1 未清项、未测项和下一步。权限批准/生产接入/外发与真实部门签认不可自动代替；缺少这些输入不阻塞其他可安全推进项，但相关项保持待批准/待确认。
